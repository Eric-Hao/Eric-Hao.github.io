2. Background & motivation论文背景与动机

Key concepts: what does correctness mean for a generated website?

A page can render beautifully while its search button cannothing; a repair can hide a visual symptom while leaving the faulty state transition intact. Code-only tests miss appearance, and screenshot similarity misses interaction. WebCompass organizes evaluation around three real development activities: create a repository from requirements, modify an existing repository, and repair a defect without breaking what already works. It is a benchmark and evaluation protocol, not a new coding model or a training algorithm.

必要概念：生成的网站怎样才算正确？

页面可能十分漂亮，但搜索按钮没有作用；修复也可能只是遮住视觉症状，而错误的状态转换仍在。仅测试代码会遗漏外观，仅比较截图会遗漏交互。WebCompass 围绕三种实际开发活动组织评估：根据需求新建仓库、修改已有仓库、修复缺陷并避免破坏既有能力。它是基准和评估协议，不是新的编程模型或训练算法。

3. The core method核心方法 / 模型详解

How to read Figure 4: where the benchmark’s task specifications come from

如何读图 4：基准的任务规格来自哪里？

Key observation and interpretation. Figure 4 has separate construction paths. Text-generation requests are deduplicated with BGE-M3 embeddings and clustering, assigned domains using five independent LLM labels, stratified, and expanded into content/interaction/visual design documents. Images capture pages and state changes; video examples follow manually planned interaction paths. Editing/repair start from WebRenderBench prototypes: total code length 32k–64k characters, each file ≤48k, GPT-4o review ≥9/10 yielding 81 candidates, then human selection of 50 and expansion into single-/multi-page variants. This supports more explicit, reproducible requirements, but a limitation is that filtering and rewriting can favor a particular style of website and reduce the ambiguity present in real customer requests.

关键观察与解释：图 4 中各任务有不同构建路线。文本生成请求经 BGE-M3 嵌入与聚类去重，使用五次独立模型标注确定领域，分层采样，再扩写为内容/交互/视觉设计文档。图像捕获页面和状态变化，视频则遵循人工规划的交互路径。编辑/修复从 WebRenderBench 原型出发：代码总长 32k–64k 字符，每文件不超过 48k，GPT-4o 评分至少 9/10，筛出 81 个候选，再由人工选择 50 个并扩展为单页/多页版本。这提高了需求清晰度与可复现性，但筛选和改写也可能偏向某类网站，并减少真实客户需求中的歧义。

Repair by controlled corruption

The authors inspect 200 real community submissions to define defect categories, then introduce defects into clean prototypes. Exact search/replace annotations map the buggy repository back to its clean target. For editing, requests specify desired UI changes, interaction flow and state feedback while omitting implementation details such as selectors and CSS values. Repair therefore has a known reference; generation remains more open-ended. A reversible injected patch makes the reference reproducible, not mathematically the only correct solution: different implementations can satisfy the same user-visible requirement.

通过受控破坏构造修复任务

作者检查 200 份真实社区提交以确定缺陷类别，再向干净原型注入缺陷。精确的搜索/替换标注把错误仓库映射回干净目标。编辑需求说明希望改变的界面、交互流程和状态反馈，同时不泄露选择器、CSS 数值等实现细节。因此修复有已知参考，而生成更开放。可逆的注入补丁使参考答案可复现，却不意味着它在数学上是唯一正确解：不同实现也可能满足相同的用户可见需求。

What the nine dimensions measure

Generation: RUN asks whether the site runs, SPI whether specifications are implemented, DSQ whether the design is good. Editing: ITG asks whether the requested change was targeted, FTI whether new and existing features work, STC whether the edit fits the requested style. Repair: RCT asks whether the root cause was addressed, ITI whether interaction integrity is preserved, RFF whether the fixed result matches the reference. Similar-sounding dimensions are not interchangeable: preserving old interactions is easier than implementing an entire new interaction flow.

九个维度分别衡量什么

生成：RUN 看能否运行，SPI 看规格是否实现，DSQ 看设计质量。编辑：ITG 看是否针对所要求的修改，FTI 看新增与已有功能是否正常，STC 看编辑是否符合所需风格。修复：RCT 看是否解决根因，ITI 看交互完整性是否保留，RFF 看修复后是否符合参考。名字相近的维度不能互换：保留旧交互与实现全新交互流程难度不同。

Equation 1: a weak requirement should matter

Here sᵢ is a checklist-item score, mᵢ its maximum, rᵢ the normalized value and n the number of items. The harmonic mean penalizes a weak item more than an arithmetic mean. For two 10-point items scored 10 and 5, the result is 2/(1+2)=0.667 rather than 0.75. If the second item scores zero, smoothing substitutes 1/10, giving 2/(1+10)=0.182 rather than a total collapse to zero. This is a worked calculation, not an additional experiment. The smoothing is scale-sensitive: a zero on a 5-point item becomes 0.2, while a zero on a 10-point item becomes 0.1.

The formula is applied separately within each dimension. Table 3’s Overall is the arithmetic mean of nine dimension scores. Figures 8–10 use harmonic combinations of the three dimensions for the relevant task or subtask before aggregation. Do not describe the whole leaderboard with one undifferentiated “harmonic score.”

其中 sᵢ 是检查项得分，mᵢ 是满分，rᵢ 是归一化得分，n 是项目数。调和平均比算术平均更惩罚薄弱项。两个满分 10 分的项目分别得 10 和 5 时，结果是 2/(1+2)=0.667，而非 0.75。第二项为零时，平滑替换为 1/10，结果为 2/(1+10)=0.182，而非整体归零。这是演算例子，不是额外实验。平滑与尺度有关：5 分项目的零分变成 0.2，10 分项目的零分则变成 0.1。

公式在每个维度内部单独计算。表 3 的 Overall 是九个维度得分的算术平均。图 8–10 对相应任务或子任务的三个维度使用调和组合，再作汇总。不能用一个没有区分层次的“调和分数”描述全部榜单。

Worked evaluation flow: a search interface

Consider an illustrative requirement: typing a query and pressing Search must update a results list, and the layout must match a reference. A screenshot can establish initial appearance but not the transition. The generation judge freezes both expected behaviors, opens the site, types and clicks, checks the DOM before and after, then records tests and screenshots. If the implementation uses a different element ID, it may change the locator; it may not weaken “results update” into “button is visible.” The resulting functional and visual checklist scores enter separate dimension-level harmonic means.

Failure handling follows the pipeline: build failure zeros functional/visual dimensions; partial rendering limits assessment to reachable content; runtime crashes preserve evidence from initial rendering but give untestable functional items zero. The paper cannot fully resolve the precedence between every zero-failure rule and the item-level smoothing, so an exact reimplementation should inspect released scoring code rather than infer it from the equation alone.

完整评估流程示例：搜索界面

设一个说明性需求：输入查询后点击 Search 必须更新结果列表，且布局符合参考图。截图能证明初始外观，却不能证明状态转换。生成裁判先固定两个预期行为，打开网站，输入并点击，对比操作前后的 DOM，再记录测试和截图。若实现使用不同元素 ID，可以改变定位方式；但不能把“结果更新”放宽成“按钮可见”。随后，功能与视觉检查得分分别进入各自维度的调和平均。

失败处理遵循执行链：构建失败时功能/视觉维度归零；局部渲染失败时只评估可达内容；运行中崩溃可保留初始渲染证据，但无法测试的功能项记零。论文未完全明确每种零分失败规则与项目平滑的优先关系，因此精确复现应检查公开评分代码，不能只由公式推断。

How to read Table 3: overall leadership hides different strengths

如何读表 3：整体领先掩盖了不同能力结构

Key observation and interpretation. Across ten tested models, Overall is 67.40 for Claude-Opus-4.5, 66.68 Gemini-3-Pro, 65.42 Gemini-3-Flash, 61.90 GPT-5.2 and 57.12 Claude-Sonnet-4.5. How to read Table 4: judge agreement has a price and a scope

如何读表 4：裁判一致性有成本，也有适用范围

Key observation and interpretation. On a 200-sample human-labeled subset, Opus-4.5 judge correlations are 0.93/0.94/0.96 for generation/editing/repair, versus Sonnet 0.88/0.90/0.89 and Haiku 0.76/0.79/0.81. Boundary: these are category-averaged scores, not independent success probabilities, and category overlap/aggregation can change the apparent ranking. The text says Gemini leads all eleven repair categories, but Figure 10 visibly gives Opus a higher bar for Missing Attributes (and Text Overlap/Loss of Interactivity); preserve the plotted exceptions rather than repeating an absolute claim.

关键观察与解释：图 9 用逐子任务调和分数比较 16 种编辑操作：页面转换、粒子特效等动画操作通常比购物车、多步向导更难。图 10 比较 11 类修复：语义错误与拥挤较弱，文字重叠及交互丢失较强。这支持区分动态协调与局部修复。它们是类别平均分，不是独立成功概率，类别重叠和汇总方式也会改变表观排名。文字称 Gemini 在全部十一类修复领先，但图 10 中 Missing Attributes（以及 Text Overlap/Loss of Interactivity）的 Opus 柱更高，应保留图上的例外，而非重复绝对化结论。

How to read Figures 11–12: difficulty attacks implementation, not just rendering

如何读图 11–12：难度首先冲击实现，而不只是渲染

Key observation and interpretation. Figure 11 groups overall scores by easy/medium/hard across the three task families; harder tasks broadly reduce performance and Qwen remains weaker, especially on editing. Figure 12 separates generation dimensions: specification implementation shows a large difficulty gradient, with Gemini-Pro dropping from 89.83 on easy to 37.64 on hard in the reported text. This supports the importance of multi-step user flows and simultaneous requirements. It cannot prove task complexity is the sole cause: difficulty labels also co-vary with content and design choices, and a few visual-quality bars are not strictly monotone.

关键观察与解释：图 11 按三类任务的简单/中等/困难分组展示总体分数；任务更难时性能总体下降，Qwen 仍较弱，编辑尤其明显。图 12 拆开生成维度，规格实现的难度梯度很大，正文报告 Gemini-Pro 从简单任务 89.83 降到困难任务 37.64。这支持多步用户流程和同时满足多个需求的重要性，但不能证明任务复杂度是唯一原因：难度标签与内容及设计选择共同变化，少数视觉质量柱也并非严格单调。

How to read Figures 13–14: preserve interactions is not the same as make the right repair

如何读图 13–14：保留交互不等于正确修复

Key observation and interpretation. Figure 13 breaks editing into targeting, feature integrity and style, all generally declining with difficulty. Figure 14 keeps repair interaction integrity relatively high while root-cause targeting and reference fidelity drop on hard tasks. This supports a gap between “the old page still responds” and “the intended defect is correctly fixed.” It cannot let us compare identically named visual axes across tasks as if they shared a rubric: edit style and repair-reference matching ask different questions.

关键观察与解释：图 13 把编辑拆为目标定位、功能完整性和风格，难度上升时总体下降。图 14 中修复交互完整性相对较高，而困难任务的根因定位和参考保真下降。这支持区分“旧页面还能响应”与“目标缺陷被正确修复”。不能因此把不同任务中听起来相似的视觉维度当作同一评分标准：编辑风格与修复参考匹配问的是不同问题。

How to read Figures 15–16: patch size and reliability are separate from average quality

如何读图 15–16：补丁规模和可靠性不同于平均质量

Key observation and interpretation. Figure 15’s violins show changed lines and contiguous diff hunks; the white dot is the median and thick segment the interquartile range. Editing median changed lines span roughly 646–1,976, versus 16–19 for repair. Repair distributions have tails beyond the human reference. This supports monitoring unnecessary edits, but a larger patch is not itself proof of worse correctness. Figure 16 then reports minimum scores across n=2 or 4 independently sampled outputs: Gemini falls about 67.0→53.6, Qwen235B about 39.9→27.8. This supports a reliability gap hidden by average scores. Boundary: Worst-of-n is a stress metric, not the probability a single user will receive the worst sampled result.

关键观察与解释：图 15 的小提琴图展示改动行数与连续 diff 块数，白点是中位数，粗线是四分位区间。编辑改动行数中位数约为 646–1,976，修复则为 16–19。修复分布在人工参考之外有长尾。这支持监控不必要的修改，但较大补丁本身不能证明正确性更差。图 16 随后报告独立采样 n=2 或 4 次输出的最低分：Gemini 约从 67.0→53.6，Qwen235B 约从 39.9→27.8。这说明平均分掩盖可靠性差距。但 Worst-of-n 是压力指标，不是单个用户拿到最差样本的概率。

How to read Table 8: which dimensions degrade in the worst sample?

如何读表 8：最差样本中哪些维度下降？

Key observation and interpretation. Table 8 decomposes the stability result. Gemini’s repair RCT falls 50.95→31.31 from Pass@1 to W@4, a 38.55% relative drop; its generation SPI falls 56.90→39.80. Qwen’s edit FTI falls 24.99→14.50, a 41.98% relative drop. This supports examining tail failures in specific requirements rather than just the average curve. It also qualifies the prose that Gemini’s dimensions remain above 49%: Table 8 contains 31.31 and 39.80. “Pass@1” here denotes the paper’s single-sample score summary, not a binary unit-test pass rate. Four samples cannot estimate extreme production tails.

关键观察与解释：表 8 拆解稳定性结果。Gemini 的修复 RCT 从 Pass@1 的 50.95 降到 W@4 的 31.31，相对下降 38.55%；生成 SPI 从 56.90→39.80。Qwen 编辑 FTI 从 24.99→14.50，相对下降 41.98%。这支持逐项检查尾部失败，而非只看平均曲线。同时也限定了正文“Gemini 所有维度仍高于 49%”的说法：表 8 明确有 31.31 和 39.80。这里 Pass@1 是论文对单样本得分汇总的命名，不是二元单元测试通过率。四次采样也无法估计极端生产尾部风险。

How to read Table 5: vision-language training trades strengths on text-only tasks

如何读表 5：视觉语言训练在纯文本任务上也有取舍

Key observation and interpretation. On the text-only subset, Qwen3-VL-32B scores 36.49 overall versus Qwen3-32B’s 31.60, with better visual and edit/repair scores, while generation RUN is lower (44.48 versus 56.28). This supports complementary capabilities rather than unconditional multimodal superiority. Boundary: this is a comparison of two trained models, not a controlled causal ablation of vision alone. Separately, Table 3’s 235B Thinking variant raises RUN 61.26→63.86 but lowers SPI 42.14→35.02 and Overall 41.14→38.78. The authors attribute omissions to attention dilution from longer reasoning, but no controlled chain-length intervention establishes that causal explanation.

关键观察与解释：在纯文本子集上，Qwen3-VL-32B 总分为 36.49，Qwen3-32B 为 31.60；前者视觉及编辑/修复较好，但生成 RUN 较低，为 44.48 对 56.28。这支持能力互补，而非多模态模型无条件更强。它比较两个已训练模型，不是仅改变视觉训练的受控因果消融。另外，表 3 的 235B Thinking 变体使 RUN 从 61.26→63.86，却让 SPI 从 42.14→35.02、Overall 从 41.14→38.78。作者将遗漏归因于长推理导致注意力稀释，但没有控制推理链长度的干预来确立该因果解释。

How to read Figures 17–18: error composition changes with modality

如何读图 17–18：错误构成随模态改变

Key observation and interpretation. Figure 17 stacks counted generation errors; feature omissions and resource failures occupy roughly 40–55% for many models. Stronger models reduce fundamental errors, leaving a larger fraction of fine-grained visual issues. Figure 18 splits text/image/video: text emphasizes missing functionality, images emphasize layout and fidelity, video combines functional and visual difficulties. This supports different verification priorities by input type. Counts are judge-derived deductions and can include multiple errors per task; a larger visual-error share can occur because other errors decreased, not because visual ability became worse.

关键观察与解释：图 17 堆叠生成错误计数；许多模型的功能遗漏与资源失败约占 40–55%。较强模型减少基础错误后，细粒度视觉问题占比上升。图 18 拆为文本/图像/视频：文本侧重缺失功能，图像侧重布局和保真，视频同时涉及功能与视觉。这支持按输入类型安排验证重点。但计数来自裁判扣分，一个任务可对应多个错误；视觉错误占比变大，也可能只是其他错误减少，而非视觉能力变差。

How to read Figures 19–20: editing fails by omission, repair by unresolved defects

如何读图 19–20：编辑常漏功能，修复常未解决缺陷

Key observation and interpretation. Figure 19’s blue regions show missing/incomplete features dominating edit deductions; for the weakest Qwen variants, missing features reach roughly three quarters of the error count. Figure 20 introduces repair-specific pink categories: defect not addressed, partially addressed and newly introduced defects, which dominate the repair profile. This supports checking requirement completion and regression separately rather than trusting a successful build. Boundary: the panels are error-count distributions, not causal diagnoses independently verified by humans; automated categorization inherits judge ambiguity and task-taxonomy choices.

关键观察与解释：图 19 的蓝色区域显示编辑扣分以功能缺失/不完整为主；较弱 Qwen 变体的功能缺失约占错误数四分之三。图 20 加入修复专用粉色类别：缺陷未解决、部分解决、新引入缺陷，并在修复构成中占主导。这支持分别检查需求完成度与回归，而不是相信构建成功就完成任务。这些是错误计数分布，并非经人工独立确认的因果诊断；自动分类会继承裁判歧义和任务分类选择。

5. Contribution & impact论文的贡献与影响

Contribution: evaluate the artifact, not just the answer

WebCompass’s main contribution is the joint evaluation of repository changes, rendered appearance and executable behavior across a broader task lifecycle. Checklist immutability, selector-only adaptation and evidence requirements make agentic judging more auditable than an unconstrained “does this look good?” judgment. Controlled defect construction gives repair a reproducible reference.

The limits are equally practical: a selected prototype pool, synthetic corruption, a finite checklist, same-family judge selection, evaluator cost and several diagram/prose inconsistencies. High correlation with humans is encouraging but cannot settle benchmark validity. For a follow-up, preserve raw per-item scores and execution evidence, reconcile Figures 8/10/16 with their tables, and test evaluator robustness to alternate correct implementations, evaluator prompt injection and hidden interaction failures. These are recommended audits, not results demonstrated here.

贡献：评估实际产物，而不仅是回答

WebCompass 的主要贡献，是在更完整的任务生命周期中联合评估仓库修改、渲染外观和可执行行为。固定清单、仅调整选择器、强制证据，使智能体裁判比不受约束的“看起来好吗”更可审计。受控缺陷构造则为修复提供可复现参考。

限制也很实际：经过选择的原型池、合成破坏、有限检查清单、同家族裁判选择、评估成本，以及多处图文不一致。与人工高度相关令人鼓舞，却不等于基准有效性已经解决。后续应保留逐项原始分数与执行证据，核对图 8/10/16 和表格，并测试裁判对不同正确实现、针对裁判的提示注入和隐藏交互失败的稳健性。这些是建议的审计，不是本文已经展示的结果。

6. Conclusion结论

Final judgment. The most useful reading of WebCompass is a testing discipline: inspect what changed, run the site, exercise the required transition, and preserve evidence for each score. Its results show substantial gaps between runnability, specification completion and visual fidelity. Use those dimensions and failure cases to guide evaluation; treat the precise leaderboard and broad prose claims with the source-level qualifications above.

WebCompass 最值得带走的是一套测试纪律：检查修改、运行网站、触发要求的状态转换，并为每项得分保留证据。结果显示可运行性、规格完成度与视觉保真之间仍有明显差距。应利用这些维度与失败案例指导评估，并结合上述原文限定看待精确排名和宽泛结论。
